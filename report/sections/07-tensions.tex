\section{Design tensions and engineering justification}
\label{sec:tensions}

\textbf{Reliability vs latency.} \emph{Tension:} guaranteed delivery costs time when packets are
lost. \emph{Position:} TCP for all data; UDP only for soft-state discovery. \emph{Defence:} under
5\,\% loss the 100\,MiB file still arrived complete in every run, with the same 104\,874\,436 chunk bytes
as on a clean link, but took $474.2 \pm 143.7$\,s instead of $116.4 \pm 33.6$\,s
(Table~\ref{tab:experiments}). In \code{cap5}, 402 of 7\,935 data segments (5.1\,\%) were
retransmitted (Section~\ref{sec:failure}). For a file synchroniser a corrupt or missing file is a
failure while a slower one is not, so we accept the slowdown. It is the same for FTP: rerun on one
night, loss made meshsync 2.1 times slower and FTP 2.3 times (Section~\ref{sec:ftp}), so the cost
comes from TCP under loss, which any reliable protocol pays. The same capture shows the
other side: discovery over UDP lost kratos twice under loss, which is harmless because it is
refreshed every 5\,s and never closes a working TCP connection.

\textbf{Security vs performance.} \emph{Tension:} encryption and authentication add handshakes and
CPU work. \emph{Position:} HMAC challenge-response always, and TLS~1.3 as a core mode (D4, D9).
\emph{Defence:} on our network TLS showed no measurable cost: setup $0.25 \pm 0.05$\,s vs
$0.65 \pm 1.08$\,s plain, and throughput $1.23 \pm 0.29$ vs $1.06 \pm 0.17$\,MB/s, both within the
spread (Section~\ref{sec:experiments}). The bottleneck is the Wi-Fi channel, not the CPU, so the
protection costs us nothing we can measure. Plain mode is kept only for the capture and as a
baseline, where it exposes traffic after the handshake.

\textbf{Compactness vs readability.} \emph{Tension:} a binary format is small; JSON is easy to read,
debug and dissect. \emph{Position:} a fixed 12-byte binary header with JSON control bodies and raw
chunk bytes (D3). \emph{Defence:} the binary header is negligible: 12 of 154 bytes in a CHUNK\_REQ frame,
and 0.016\,\% of the 100\,MiB transfer, where TCP/IP and link headers cost 66 bytes per full segment
(Section~\ref{sec:capture}). JSON is the visible cost: in a delta sync only 75\,667 of the
171\,836 bytes received were chunk data, so metadata (mostly the index entry listing every chunk
hash) was more than half. That is the price of readable, dissectable messages, and it is still
0.16\,\% of a full copy. A binary hash list would be the first optimisation if small edits to large
files dominated.

\textbf{Connection reuse vs resources.} \emph{Tension:} persistent connections cost memory and a
thread per peer, $O(n^2)$ links in a full mesh; reconnecting per operation costs round trips.
\emph{Position:} a persistent full mesh (D6). \emph{Defence:} reaching SYNCED on a new connection takes
5 round trips in plain mode and 6 with TLS, against 1 for an operation on a live connection. With our
measured RTTs that is about 46\,ms instead of 9\,ms between kratos and defalt, and about 340\,ms instead
of 68\,ms to minipc, before any processing (a single-host pilot measured about 8\,ms plain and 52\,ms
TLS setup on top). These are model estimates from measured RTTs, not a separate experiment. At three
peers the mesh is three connections, so reuse is clearly worth it; the $O(n^2)$ cost would matter
only at a scale we do not target.
