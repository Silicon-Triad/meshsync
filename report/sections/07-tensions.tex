\section{Design tensions and engineering justification}
\label{sec:tensions}

\textbf{Reliability vs latency.} \emph{Position:} TCP for all data, UDP only for discovery.
\emph{Defence:} under 5\,\% loss, every 100\,MiB copy still arrived complete, but took longer:
474\,s instead of 116\,s in the main batch (Table~\ref{tab:experiments}), and 2.1 times longer on
the FTP night. FTP slowed by the same factor, 2.3 times, so this is the price of TCP, not of our
design. For a file synchroniser a missing or corrupt file is a failure; a slow one is not.
Discovery takes the opposite side: a lost ANNOUNCE costs nothing, because another follows 5\,s later.

\textbf{Security vs performance.} \emph{Position:} HMAC authentication always, TLS~1.3 as an
option. \emph{Defence:} on our network TLS had no measurable cost. Its throughput and setup time
were within the spread of plain mode (Section~\ref{sec:experiments}), because the Wi-Fi is the
bottleneck, not the CPU. The FTP capture shows what the alternative costs: the user name and
password crossed the network in plain text (frames 6 and 9). Our handshake sends only nonces and
MACs.

\textbf{Compactness vs readability.} \emph{Position:} a 12-byte binary header, with JSON for control
messages. \emph{Defence:} the binary header is cheap. It is 12 of 154 bytes in a CHUNK\_REQ and
0.016\,\% of the 100\,MiB transfer (Section~\ref{sec:capture}). JSON is the visible cost: after a
1\,KiB edit, the index entry listing every chunk hash was more than half of the 172\,KB sent. That
still beats a full copy by 600 times, and it keeps messages readable and easy to dissect.
% savings.md: delta all bytes 171,836, chunk 75,667; 105,183,306 / 171,836 = 612.

\textbf{Connection reuse vs resources.} \emph{Position:} keep one connection open to every peer.
\emph{Defence:} a new connection needs 5 round trips before it is usable, or 6 with TLS, against 1
on an open one. With our RTTs that is about 46\,ms instead of 9\,ms to defalt, and 340\,ms instead of
68\,ms to minipc. These are estimates from measured RTTs, not a separate test. With three peers we
hold only three connections, so reuse is clearly worth it.
