\section{Protocol specification (R1)}
\label{sec:protocol}

This section is the complete wire protocol in condensed form; \code{docs/PROTOCOL.md} in the
repository (Appendix~\ref{app:code}) adds worked examples and rationale. All multi-byte integers are
unsigned big-endian; all JSON is UTF-8. \code{peer\_id} is exactly 8 \emph{uppercase} hex
characters; every other hex value (hashes, nonces, MACs, tags) is lowercase, and the other case
is invalid. \code{K} is the group's 32-byte shared secret and never crosses the wire.
% PROTOCOL.md §1 (byte order, hex case, K); constants.py PEER_ID_HEX_LEN = 8.

\subsection{Overview}
\label{sec:proto-overview}

All peers run the same program; there is no server (D6). On each TCP connection the side that
dialled is the \emph{initiator} (I) and the side that accepted is the \emph{responder} (R); roles
matter only for the handshake and REQ\_ID numbering. When peer A learns of peer B and has no
connection to it, A dials B only if \code{A.peer\_id < B.peer\_id} (string comparison), so each pair
has one dialer. Discovery (ANNOUNCE, LEAVE) uses UDP broadcast to 255.255.255.255, port 47000;
everything else uses TCP port 47001, optionally inside TLS~1.3. Both ports are configurable, and
the TCP port in use is announced. After a connection closes, the dialer retries every 5\,s
while the peer is still in its peer table.
% PROTOCOL.md §1 (roles), §2 (transport, ports), §8.1 (dial rule), §8.4 (reconnect every
% ANNOUNCE_INTERVAL); constants.py UDP_PORT = 47000, TCP_PORT = 47001, ANNOUNCE_INTERVAL = 5.

\subsection{Discovery datagram (UDP)}
\label{sec:proto-discovery}

One datagram is one JSON object of at most 512 bytes with exactly nine fields (any other key
makes it invalid; JSON booleans are not integers): \code{magic} = \code{"MS"}; \code{ver} = 1;
\code{type} = \code{"ANNOUNCE"} or \code{"LEAVE"}; \code{peer\_id}; \code{name} (non-empty string);
\code{tcp\_port} (1--65535); \code{index\_rev} (integer $\ge 0$); \code{ts} (sender's Unix time,
seconds); \code{tag} (64 lowercase hex). The tag is
\[
  \mathit{tag} = \mathrm{hex}\bigl(\mathrm{HMAC}\mbox{-}\mathrm{SHA256}(K,\ \mathrm{canonical\_json}(\mbox{all fields except \textit{tag}}))\bigr),
\]
where canonical JSON has keys sorted by code point, separators exactly \code{,} and \code{:} with no
whitespace, and non-ASCII written as raw UTF-8. The receiver recomputes it over the fields it
parsed, not over the received bytes. \textbf{Receive rules}, applied in order; the datagram is
silently dropped at the first that fails: (1)~length $\le$ 512 bytes, valid UTF-8 JSON, exactly
the nine fields with valid types; (2)~\code{peer\_id} differs from the receiver's own (its own
broadcast echoed back); (3)~\code{tag} equals the recomputed tag (constant-time comparison);
(4)~$|\mathit{now} - \mathit{ts}| \le 30$\,s; (5)~\code{ts} is greater than the last accepted
\code{ts} from this \code{peer\_id} (replay); (6)~if \code{type} = LEAVE, remove the peer from the
peer table; (7)~if \code{type} = ANNOUNCE, add or update the peer (name, address, port,
\code{index\_rev}, last-seen time).
The peer's address is the datagram's source IP, never a body value; the last accepted \code{ts} is
kept after LEAVE or expiry. Each peer sends ANNOUNCE every 5\,s and one LEAVE at shutdown, with
$\mathit{ts} = \max(\lfloor\mathit{now}\rfloor, \mathit{last\_sent\_ts}+1)$; a peer not heard for more
than 15\,s is removed. Leaving the peer table never closes a TCP connection.
% PROTOCOL.md §3.1 (fields), §3.2 (tag, D11), §3.4 (receive rules), §3.5 (timers);
% constants.py MAX_DATAGRAM = 512, ANNOUNCE_MAX_SKEW = 30, ANNOUNCE_INTERVAL = 5, PEER_EXPIRY = 15.

\subsection{TCP framing}
\label{sec:proto-framing}

Every TCP message is a 12-byte header (\code{struct} format \code{!2sBBII}) followed by a body
(Table~\ref{tab:header}). The reader reads exactly 12 bytes, validates the header, then reads
exactly \code{BODY\_LEN} bytes, looping because TCP is a byte stream.

\textbf{Validation order} (every failure is fatal, codes in Table~\ref{tab:errors}): MAGIC
$\neq$ \code{"MS"} $\rightarrow$ BAD\_HEADER; VER $\neq$ 1 $\rightarrow$ BAD\_VERSION; unknown TYPE
$\rightarrow$ BAD\_HEADER; BODY\_LEN $>$ 1\,MiB $\rightarrow$ TOO\_LARGE; body not valid JSON or not
matching its schema $\rightarrow$ BAD\_HEADER. A body must have exactly the listed keys; NaN and
Infinity are invalid and booleans are not integers. Bodies are not canonicalised.
% PROTOCOL.md §4.2, decisions (a), (c).

\textbf{REQ\_ID.} A request carries a non-zero REQ\_ID and its reply (or the ERROR answering it)
the same one, so replies may arrive in any order. The initiator uses odd IDs and the responder even
IDs; they wrap after \code{0xFFFFFFFF} and skip IDs still awaiting a reply. A received non-zero ID
with the receiver's own parity is a reply, otherwise a request. REQ\_ID 0 marks handshake
messages, NOTIFY, BYE and an ERROR not tied to a request.
% PROTOCOL.md §4.3, decision (h).

\textbf{Example.} PING with REQ\_ID 1 and body \code{\{"t": 1730473200.5\}} (19 bytes) is
\code{4d53 01 30 00000001 00000013} followed by the 19 body bytes.
% PROTOCOL.md §4.4 (generated by framing.send_msg). First thing to cut if §2 is over budget.

\subsection{Messages}
\label{sec:proto-messages}

Table~\ref{tab:msg-formats} lists every TCP message. HELLO to AUTH\_OK are legal only in state
HANDSHAKE; ERROR in any state; all others only in AUTHENTICATED or SYNCED. ``Req'' and ``Reply''
mean a REQ\_ID as in Section~\ref{sec:proto-framing}; ``0'' means REQ\_ID 0. Nonces are 16 random
bytes sent as 32 lowercase hex characters; MACs and hashes are 64 lowercase hex. An index entry is
a JSON object with exactly \code{path}, \code{size}, \code{file\_hash}, \code{chunks} (SHA-256 of each
chunk, in order), \code{version} (\code{peer\_id} $\rightarrow$ counter) and \code{deleted}.

\subsection{Legal message order}
\label{sec:proto-order}

\textbf{Connection setup} (initiator = lower \code{peer\_id}): (1) TCP connect; (2) with
\code{--tls}, the TLS~1.3 handshake; (3) I$\rightarrow$R HELLO; (4) R$\rightarrow$I HELLO\_ACK;
(5) I$\rightarrow$R AUTH; (6) R$\rightarrow$I AUTH\_OK, after which both sides are AUTHENTICATED;
(7) with TLS, each side checks the peer certificate's CN equals the peer's HELLO/HELLO\_ACK
\code{name}; (8) both sides send INDEX\_REQ and answer the other's with INDEX; on receiving INDEX
the connection is SYNCED. The whole HELLO to AUTH\_OK exchange must finish within 10\,s.
Table~\ref{tab:transitions} gives the state changes; the specific failure cases are in
Tables~\ref{tab:msg-formats} and~\ref{tab:errors}.

silently dead peer is noticed after about 30\,s. If two authenticated links to the same peer

\subsection{Error codes}
\label{sec:proto-errors}

An ERROR body is \code{\{"code": int, "msg": string\}}. For a fatal code the sender sends ERROR and
closes; the receiver closes without replying. An unknown code is itself an invalid body
(BAD\_HEADER).

\subsection{Security}
\label{sec:proto-security}

\textbf{HMAC challenge-response} (D4). Each side proves it knows \code{K} by MACing the
\emph{other} side's fresh nonce:
$\mathit{mac\_r} = \mathrm{HMAC}\mbox{-}\mathrm{SHA256}(K, \mathtt{0x52} \,\|\, \mathit{nonce\_i} \,\|\, \mathit{nonce\_r})$ and
$\mathit{mac\_i} = \mathrm{HMAC}\mbox{-}\mathrm{SHA256}(K, \mathtt{0x49} \,\|\, \mathit{nonce\_r} \,\|\, \mathit{nonce\_i})$.
The 33-byte input is the ASCII role byte (\code{"R"} or \code{"I"}) then the two nonces as raw
(hex-decoded) bytes; the role byte stops a MAC being reflected back. Nonces come from a
cryptographic RNG, MACs are compared in constant time, and a recorded handshake cannot be replayed.
% PROTOCOL.md §6.3, §6.4 (decision (g)).

\textbf{TLS mode} (D9, \code{--tls}; \code{--plain} is the default). Right after connect/accept and
before HELLO, both sides run TLS~1.3 (minimum version) with mutual certificates
(\code{CERT\_REQUIRED}) trusting only the group CA; hostname checking is off because peers dial
discovered IPs. The HMAC handshake then runs inside TLS, followed by the CN check above. Both
peers must use the same mode. Plain mode exists for the packet capture (R5) and as a measurement
baseline; in it, traffic after the handshake is neither encrypted nor integrity-protected.
% PROTOCOL.md §6.2 (decision (e)), §11.2 (plain mode limits); PROJECT_CONTEXT.md D9.
