\section{System and deployment architecture (R3)}
\label{sec:architecture}

Each host runs one meshsync peer: discovery and peer management, one connection object per peer
(TCP socket, reader thread, send lock, REQ\_ID table), the sync engine with its index and chunk
store, and the transfer scheduler. We deployed it on three independent Linux machines on one
Wi-Fi LAN, 192.168.100.0/24 with gateway 192.168.100.1, the network we will demonstrate on
(Figure~\ref{fig:network}, Table~\ref{tab:ip-plan}). The session ran on 12 November 2026 with
\code{main} at commit \code{79854e6}; its raw evidence is in \code{data/deploy/} in the repository.

\textbf{Run configuration.} On each host we ran \code{meshsync run --plain --log-level INFO}, then
\code{meshsync run --tls --log-level INFO}, with \code{tcp\_port=47001}, \code{udp\_port=47000},
\code{chunking='cdc'} and no static peers (\code{peers=()}), so every connection was found by UDP
discovery. For TLS, \code{scripts/gen\_certs.sh} made the group CA and certificates on kratos; each
host received the CA certificate, its own certificate and key, and the secret over \code{scp}, and
the CA key stayed on kratos. Excerpts from minipc's plain run and defalt's TLS run (date and
logger prefixes shortened with ``\ldots''):
