\section{System and deployment architecture (R3)}
\label{sec:architecture}

We ran meshsync on three separate Linux machines on one Wi-Fi LAN, 192.168.100.0/24, with the
router at 192.168.100.1 (Figure~\ref{fig:network}, Table~\ref{tab:ip-plan}). This is the network
we will demonstrate on. The raw evidence is in \code{data/deploy/} in the repository.

The IP configuration as captured with \code{ip -4 addr} (one line per host):
\begin{verbatim}
kratos: inet 192.168.100.92/24 brd 192.168.100.255 ... wlp2s0
minipc: inet 192.168.100.190/24 brd 192.168.100.255 ... wlp2s0
defalt: inet 192.168.100.80/24 brd 192.168.100.255 ... wlp4s0
\end{verbatim}
% data/deploy/<host>/host.txt ("## ip -4 addr"), host name prefixed, flags shortened to "...".

\textbf{Run.} Each host ran \code{meshsync run}, first with \code{--plain} and then with
\code{--tls}, with no static peers. So every connection was found by UDP discovery. For TLS, kratos
made the group CA and each host's certificate. All three links reached SYNCED in both modes, for
example on minipc:
\begin{verbatim}
20:27:29,272 ...auth: initiator handshake ok with defalt (BDB9C75B)
20:27:29,273 ...manager: peer up: defalt 192.168.100.80:47001 (plain)
20:27:29,285 ...connection: connection to defalt is SYNCED
\end{verbatim}
A file created on minipc, edited on defalt and deleted on kratos reached the other hosts each
time. Over TLS, a new file had the same SHA-256 on all three.
