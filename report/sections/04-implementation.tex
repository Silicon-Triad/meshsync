\section{Implementation notes (R2, R4)}
\label{sec:implementation}

\textbf{Socket API only (R2).} meshsync is Python 3.11+ on the standard library only (D1, D15).
Both transports are written directly on the \code{socket} module: a UDP datagram socket for
discovery and blocking TCP stream sockets with timeouts for data, using \code{threading} rather
than asyncio or any networking framework (D1). No application-protocol library is used: the
message format, framing, handshake and state machine are ours. The other modules are helpers for
data formats and cryptography, not protocols: \code{struct} packs and unpacks the 12-byte header,
\code{json} encodes datagrams and message bodies, \code{hashlib} computes SHA-256 of chunks and
files, \code{hmac} computes discovery tags and handshake MACs and compares them in constant time,
and \code{ssl} wraps our own TCP sockets in TLS~1.3 without changing the meshsync messages inside.
% PROJECT_CONTEXT.md §2 (R2 row: hashlib/hmac/ssl/json/struct are helpers), §4 D1, D15.

\textbf{Threads.} Each connection object owns its socket, its state, one reader thread that
receives and dispatches messages, a send lock that serialises all writes, and the table of
outstanding REQ\_IDs. Replies are matched to requests by REQ\_ID, so several requests (up to 8
CHUNK\_REQs per peer) are in flight at once on one connection.
% PROJECT_CONTEXT.md §8.2 (connection.py: socket, state, reader thread, send lock, REQ_ID map),
% §8.3 (Connection.request -> Future); constants.py MAX_OUTSTANDING_PER_PEER = 8.

\textbf{Key decisions.} Fixed binary header with JSON control bodies and raw chunk bytes (D3);
HMAC-SHA256 challenge-response on a shared secret (D4); pure peer-to-peer full mesh, no server
(D6); TLS~1.3 with mutual certificates as a core mode, plain mode kept for capture and baseline
(D9); HMAC-tagged, timestamped discovery (D11); version vectors so that no decision compares clocks
across hosts (D2).

Reliable data transfer
  & Not needed: discovery is soft state. A lost ANNOUNCE is replaced 5\,s later, and expiry
    after 15\,s tolerates lost datagrams. \emph{With TCP:} a connection needs the peer's address
    first, which is exactly what discovery has to find; TCP cannot broadcast.
  & Required: index entries and chunks must arrive complete and in order. TCP retransmits and
    orders; SHA-256 per chunk adds an end-to-end check. \emph{With UDP:} we would have to build
    sequence numbers, acknowledgements, retransmission and reordering, and split each chunk of up
    to 256\,KiB across many datagrams. \\
Throughput
  & Tiny datagrams ($\le$ 512 bytes) every 5\,s. \emph{With TCP:} one connection per pair just to
    say ``I am here'', with its handshake and kept state, for no data.
  & Bulk chunk transfer needs congestion and flow control; one persistent connection per pair
    avoids repeated handshakes. \emph{With UDP:} we would need our own congestion control or
    flood the shared Wi-Fi, and our own flow control. \\
Timing
  & One broadcast reaches every peer at once, with no setup, so a new peer appears within
    seconds. \emph{With TCP:} a separate connection setup to every peer, each one only possible
    after its address is known.
  & Sync is seconds-level, so TCP's retransmission delay is acceptable; REQ\_ID multiplexing
    removes head-of-line blocking between requests on one connection. \emph{With UDP:} lower
    per-message latency that seconds-level sync does not need. \\
Security
  & Broadcast is visible to all, and TLS needs a connection, so each datagram carries an HMAC tag
    and timestamp (30\,s window, replay check). \emph{With TCP:} TLS would be possible, but only
    after the address problem above.
  & HMAC challenge-response proves knowledge of the secret, and TLS~1.3 runs over the TCP
    stream, adding encryption and certificate checks. \emph{With UDP:} TLS, which needs a reliable
    byte stream, could not be used as is. \\
