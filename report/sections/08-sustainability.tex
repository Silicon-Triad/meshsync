\section{Sustainability and efficiency analysis}
\label{sec:sustainability}

\textbf{Measured savings.} After a 1\,KiB overwrite of the 100\,MiB file, delta sync sent 75\,667
chunk bytes instead of 104\,874\,436 for a full copy, saving 99.93\,\% of chunk data and 99.84\,\% of all
bytes received (171\,836 vs 105\,183\,306, metadata included). After a 1\,KiB insert at offset 0,
content-defined chunking sent 66\,594 chunk bytes where fixed-size chunking re-sent 104\,877\,836, because
the insert shifts every fixed chunk boundary: 99.94\,\% saved, 99.85\,\% of all bytes (162\,562 vs
105\,122\,508). Each value is the mean of n = 5 runs; byte counts did not vary between runs.
% analysis/out/savings.md; analysis/out/full_delta.md, fixed_cdc.md.

\textbf{Projection.} \emph{Assumption} (PROJECT\_CONTEXT.md §13): 10\,000 users, each making 20 edits
a day, each edit like ours (a small change to a 100\,MiB file) and synced to one other peer. That is
200\,000 edits a day. Using all bytes received per edit:
\begin{itemize}\itemsep0pt
  \item full copy: $200\,000 \times 105\,183\,306$\,B = 21\,036.7\,GB/day, 7\,678\,381\,GB/year;
  \item delta sync: $200\,000 \times 171\,836$\,B = 34.4\,GB/day, 12\,544\,GB/year;
  \item saved: 21\,002.3\,GB/day, about 7\,665\,837\,GB (7.67\,PB) a year.
\end{itemize}
(1\,GB = $10^9$ bytes, 365 days.) The CDC-vs-fixed comparison after an insert gives almost the same
saving (20\,992.0\,GB/day).
% 10,000 x 20 = 200,000; 105,183,306 x 200,000 = 2.1037e13 B; 171,836 x 200,000 = 3.4367e10 B;
% (105,183,306 - 171,836) x 200,000 x 365 = 7.6658e15 B; CDC: (105,122,508 - 162,562) x 200,000.

\textbf{Assumptions, uncertainty and the counter-weight.} The projection is only as good as its
inputs: real edits are rarely to 100\,MiB files, many edits touch small files where delta and full
copy are close, and a 3-peer group would send each edit to two peers, not one. The figures are
therefore an upper-bound illustration of scale, not a forecast. Their direction is robust: for
small edits to large files, sending changed chunks instead of whole files removes almost all of the
traffic. The counter-weight is CPU: every peer hashes each file it scans, and CDC additionally runs a
rolling hash over every byte to find chunk boundaries, which costs energy on every edit even when no
bytes are saved. We did not measure CPU time or energy, so we cannot net this off against the
network saving; that is a limitation of this analysis.
